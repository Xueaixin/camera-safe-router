# 北京图与高德界外拼接方案

更新时间：2026-08-14
状态：**已定稿并切换为正式环境**（北京图 + 北京版 schema v4 边界 + `beijing-compliant-time-v2` 正式缓存；2026-08-14 正式化，分支 `dev-amap-external`）

## 1. 目标

把自研路网从京津冀缩小到北京市范围，受控区内路线（六环+通州）继续由自研引擎保证合规与硬约束；受控区外路线不再自研，参考路线由高德 JS API（`AMap.Driving`，复用现有前端 key）渲染，真实导航由高德 URI 跳转承担，从而：

- 后端图数据与内存占用显著减小（北京 PBF 约 39MB，京津冀约 177MB；北京图预计边数约为京津冀的 30~35%）；
- 界外参考路线不局限于京津冀（高德全国覆盖），真实导航由高德承担；
- 后端保持零高德服务端依赖（不使用高德路径规划 Web API）。

## 2. 场景定义（新方案下的处理）

| 场景 | 起终点 | 处理方式 |
|---|---|---|
| 1 | 均在界外 | 后端 `/routes` 用北京路网规划真实路线（界外部分摄像头解禁，按可通行路网计算）；任一点超出北京路网则返回 `OUTSIDE_ROUTING_BOUNDS` 提示；不调用高德路线规划（不消耗配额），完整导航仍由“高德导航”入口承担 |
| 2 | 均在界内 | 自研受控内段路线（现状保留） |
| 3 | 界内↔界外 | 自研受控内段 + 出界点/入界点；界外段由前端高德 API 渲染参考路线，真实导航由“高德导航”跳转承担 |

说明：场景 3 的“界外段”仅作参考，最终以高德导航为准；自研路线不再包含界外 geometry，前端“完整行程”视图改为“受控内段 + 高德界外参考线 + 高德导航入口”。

## 3. 架构变化

### 3.1 后端

- 图数据：京津冀 PBF → 北京 PBF（`osm/beijing-latest.osm.pbf`，sha256 `4def5795…`）；重新构图，缓存目录独立（建议 `graph-cache/jingjinji-compliant-time-v2-beijing` 或按北京命名）。
- 边界：`sourcePbfSha256` 绑定 PBF，换北京图后必须重新生成并集边界（schema v4 含 `provincial_border`）。
- 出界点/入界点：候选集基于新图重新审计（当前京津冀图下出界 349、入界 272 普通口，北京图下需重新确认）。
- 受控内段搜索、摄像头硬避让、收费站走廊、互转走廊、省界规则：全部保留，仅图范围变化。
- 界外规划链路：摘除/简化——出界点选择、导航交接点、完整行程组装、形状终检、参考路线兜底均不再依赖界外 A*。

### 3.2 前端

- 完整行程：自研受控内段（实线）+ 界外高德参考路线（前端 `AMap.Driving`）；两条线在交接点坐标处首尾相连，视觉上为一条完整行程。
- **配色与交互（已定稿）**：选中的路线界内段与界外段统一主色；未选中的备选界外路线浅色/半透明；点击备选路线切换，切换后选中线恢复主色。
- 真实导航：交接点弹窗“高德导航”按钮保持现有 `uri.amap.com/navigation` 跳转（`mode=car`，`callnative` 参数不动），负责界外真实导航；界外参考线标注“界外路线规划由高德导航提供”。
- 环内行程视图保留；总距离/时长仅统计受控内段，界外参考线展示高德返回的距离/耗时。
- 交接点交互：出界点即交接点，保留“设为起点/终点/复制位置/高德导航”。

## 4. 出界点选择方案（不依赖界外 A*）

在现有 `Dmin+1000` 分层候选基础上：

1. 方向过滤：计算“起点→界外终点”方位角，剔除方位差超过阈值（默认 90°）的出界口；
2. 界外粗评：剩余候选按“界内搜索距离/时间 + 界外直线距离（haversine 出界口→终点）× 权重（默认 1.0）”评分取最优；
3. 兜底：某层候选全部被方向过滤时，放宽方向阈值或扩层。

成本：O(候选数)，毫秒级；不调用高德 API、不跑界外 A*。界外直线距离在高速网为主的界外区域与真实路程强相关，方向过滤保证不选反向出口。

### 4.1 POC 验证结论（2026-08-14，北京图，12 个真实跨界场景）

`BeijingExitPointSelectionPocTest` 在北京图（`graph-cache-beijing-test`）+ 北京版 v4 边界上执行东/南/西/北 + 朱辛庄↔龙意园 + 华为↔龙意园共 12 个场景：

- **全部场景均可选出通行口，界内段连续组装成功，单场景 24~376ms**（不含图加载），完全不再依赖界外 A*；
- **界外端点超出北京图的 4 个场景（朱辛庄↔龙意园、华为↔龙意园）现行界外 A* 根本无法评估**，新方案正常选出北六环（小汤山/兴寿一带）与西侧（大觉寺/军庄一带）通行口——这正是本方案的核心价值；
- 界外端点在图中时（南、北、西南向），南/北向 4 个场景新选点与现行 A* 选点一致；西向入界新选点（莲石湖西路）与 A* 择优略异，但方向一致；
- **方向过滤 90° 对出界方向过严**：华为→龙意园真实最优出口在西侧（大觉寺/军庄一带，方位差约 138°），会被 90° 过滤掉而走兜底；建议 **出界方向阈值放宽（默认 135~180°）或直接按评分选点，入界方向保持 90°**（入界点应尽量靠近界内终点的方向侧）；
- **交接点净空多数达不到 250m**：沿通行口所在边界边向界外延伸，得到点均在界外，但净空多在 20~170m（边界边较短，250m 目标需要沿界外道路网继续延伸）；
- 报告：`workspace/work/beijing-validation/exit-point-selection-poc.md`。

### 4.2 交接点（高德导航起/终点）方案

现行 `NavigationHandoffSelector` 依赖界外 A* 参考路线来寻找 250m 净空的普通道路/高速点；去掉界外 A* 后：

1. **基础方案（已验证）**：通行口所在边界边向界外延伸，取“界外、沿路 500m 内”的最优点作为交接点。优点是零额外搜索；缺点是净空多在 20~170m，达不到 250m 品质目标；
2. **增强方案（建议实现）**：从通行口沿界外“释放连接器”（released connector，北京图 4850 条）做**有界 500m 的向外行走**，优先同一条道路/同等级道路，找到净空 ≥250m 的点；找不到则回退到基础方案的最优点。该行走只使用北京图内数据，毫秒级；
3. 50m 摄像头解禁安全边距是硬约束底线，250m 是导航品质偏好——若增强方案在某些口仍不足 250m，可接受“界外 + 净空 ≥50m”的交接点。

## 5. 界外路线与高德“多路线”问题

### 5.1 当前结论（免费 URI 路线）

- 高德 URI 导航打开后由高德 App/网页提供**多条可选路线**，用户自行选择；URI 层无法、也无需筛选路线——界外段定位为参考，最终路线以用户在高德中选定的为准。
- 前端“高德导航”按钮已实现该跳转，界外段即“从出界点/交接点导航到界外终点”。

### 5.2 待调研项：高德可能给出“穿过受控区”的界外路线

界外导航起点位于受控区边界（出界点），高德规划的路线理论上可能先进入受控区（例如走六环内或通州内部）再出界，与“界外应尽量不进入受控区”的预期冲突。需要调研：

- 高德 URI/API 是否支持“途经规避”或“起点偏移”来约束路线不进入受控区；
- 若不支持，评估接受度：界外段本就以高德导航为准，高德给出更快但穿界的路线时是否可接受；
- 备选：后端用高德路径规划 API（需服务端 key + 配额）获取路线后按受控区交叉过滤，仅保留不穿界的方案（回到“后端依赖高德”的权衡）。

**调研结论（2026-08-14）**：高德 URI API 的驾车导航仅支持 `policy` 参数（0=推荐、1=避免拥堵、2=避免收费、3=不走高速，且 3 仅移动端），**不支持规避区域/途经点约束**；URI 打开后由高德 App/网页展示多条可选路线，用户自选。因此：

- 免费 URI 路线无法在 URI 层筛选“不穿过受控区”的方案；
- 若必须程序化筛选/规避受控区，只能使用高德 Web 服务路径规划 API（需要服务端 key + 每日配额），按返回路线与受控区求交后过滤；
- 本方案默认接受“界外路线以高德为准、用户自选”的参考定位；是否升级到 API 过滤作为后续可选决策。

官方参数清单（[路径规划 URI API](https://lbs.amap.com/api/uri-api/guide/travel/route)）：`from`/`to` 必选，`via`（驾车模式最多 1 个途经点）、`mode`、`policy`、`src`、`callnative` 可选；**无规避区域参数**。若后续需要程序化规避受控区，应升级到高德驾车路径规划 Web API（服务端 key + 配额，支持避让区域 `avoidpolygons`），获取路线后按受控区求交过滤。

### 5.3 界外参考路线：高德驾车路径规划（已定稿，2026-08-14）

**决策（2026-08-14 更新）**：界外参考路线改用高德 JS API `AMap.Driving`（前端直接调用，复用现有 `VITE_AMAP_KEY`），路线质量优于 OSRM；真实导航仍由高德 URI 承担。界外路线定位为体验参考，不校验。

**数据源**：前端 `AMap.Driving`（`amapLoader` 加载 `AMap.Driving` 插件）。

- 起终点输入 WGS84，前端转 GCJ02 后调用；返回 GCJ02 路线（距离/耗时/geometry），前端最多保留 3 条备选；
- **多策略并行**：`AMap.Driving` 单次 `search` 只返回一条推荐路线，因此并行调用 3 个策略（`LEAST_TIME` / `LEAST_FEE` / `LEAST_DISTANCE`）各取 1 条，合并去重后最多 3 条；代价是每次跨界规划消耗 **3 次 JS API 配额**，需关注用量；
- **场景 1（起终点均在界外）不调用高德路线规划**：`/routes` 用北京路网直接规划真实路线（`EXTERNAL_ONLY` 模式，含真实几何/距离/耗时）；任一点超出北京路网时返回 `OUTSIDE_ROUTING_BOUNDS`“超出可规划范围”提示；不消耗 JS API 配额；
- 场景 1 交互：规划成功显示“界外路线规划完成”+ 小字“界外路线由服务端路网规划，仅供参考；实际导航请以高德导航为准”；超出路网时错误提示使用 warning 样式并附带“高德导航”按钮（起终点直接跳转高德）；
- 复用现有 JS API key，不需要额外申请 Web 服务 key（前端直连，后端无高德依赖）；
- 前端 mock 模式返回固定界外路线数据，不依赖网络。

**后端 EXTERNAL_ONLY 说明（2026-08-14 更新）**：场景 1（起终点均在受控区外）由 `EXTERNAL_ONLY` 轻量响应改为**真实路线规划**——走通用驾车引擎（北京路网内可吸附即返回真实几何/距离/耗时；任一点无法吸附则返回 `OUTSIDE_ROUTING_BOUNDS`“超出可规划范围”，不再拉两点直线）。因界外摄像头解禁，`EXTERNAL_ONLY` **跳过独立摄像头安全校验**（避免界外解禁摄像头被二次校验误报）；起终点 50 米摄像头避让检查仍保留。

**场景隔离原则**：场景 1/2/3 的链路互不依赖——场景 1 只走 `/routes`（不调高德）；场景 2（界内）保持自研合规路线；场景 3（跨界）才使用前端 `AMap.Driving` 三策略并行渲染界外参考路线（最多 3 条、消耗 3 次配额）。

**可用性验证（2026-08-14，真实界外段）**：

| 场景 | 主路线 | 备选路线 |
|---|---|---|
| 朱辛庄→龙意园（北侧交接点→武清） | 131.8km / 98min | 有（133.9km） |
| 华为→龙意园（西侧交接点→武清） | 137.3km / 103min | 有（134.5km） |
| 龙意园→朱辛庄（武清→北侧交接点） | 134.9km / 101min | 有（134.6km） |
| 龙意园→华为（武清→西侧交接点） | 136.8km / 106min | 有（140.7km） |

结论：OSRM 公共实例路线质量不理想，已切换为高德 `AMap.Driving`；单次搜索只返回 1 条，故按 3 个策略并行各取 1 条，去重后最多 3 条。前端兼容备选路线 0~3 条（无备选时不显示切换）。

## 6. 场景 1（起终点均在界外）

不自研规划，前端直接“高德导航”从起点到终点。后端可保留一个极简响应（例如仅返回 `EXTERNAL_ONLY` 空路线 + 高德导航入口），或由前端直接判断后发起高德导航，不再调用自研规划接口。

### 阶段一：数据与图（当前进行）

**阶段二 POC 结果（2026-08-14）**：

- 场景 1：后端可直接返回轻量响应（含高德导航入口）或前端直接判断，不自研规划。
