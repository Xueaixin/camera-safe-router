# 路线规划三方案总览

更新时间：2026-08-14

当前共有三种合理的路线规划方案，分别保存在独立分支。本文统一说明三者的路网、存储、路由链路、内存占用与取舍；各方案的详细技术文档与部署清单见对应分支。

## 1. 方案一：北京路网 + 高德 API 拼接（推荐/当前正式方案）

- 分支：`dev`（开发基线）、`dev-amap-external`（方案实现分支）
- 路网：北京 PBF（`osm/beijing-latest.osm.pbf`，约 40MB）
- 图缓存：`graph-cache/beijing-compliant-time-v2`（RAM 存储）
- 边界：`boundaries/sixth-ring-boundary.geojson`（schema v4 北京版，`sourcePbfSha256=4def5795…`）

路由链路：

- 场景 2（界内↔界内）：后端自研受控合规路线（六环+通州，摄像头硬避让、收费站走廊、省界规则）。
- 场景 1（界外↔界外）：后端用北京路网直接规划真实路线（`EXTERNAL_ONLY`）；任一点超出北京路网时返回“超出可规划范围”并提供高德导航入口。
- 场景 3（界内↔界外）：后端规划受控内段 + 出/入界交接点；界外参考线由前端高德 `AMap.Driving` 三策略并行渲染（最多 3 条，每次消耗 3 次 JS API 配额），真实导航由高德 URI 跳转承担。

内存：进程约 1GB（堆实际使用约 400MB）；2G 服务器可将 `-Xmx` 调至 1536m 运行，无需 swap。

优点：内存小、启动快（约 1.5 分钟）、界外不局限于京津冀（高德全国覆盖）。
代价：界外路线依赖前端高德 JS API key 与每日配额；`VITE_AMAP_KEY` 仅前端使用，后端无高德依赖。

技术文档：`docs/plans/北京图与高德界外拼接方案.md`
部署清单：`docs/plans/部署上线实施清单.md`

## 2. 方案二：京津冀路网 + RAM 存储 + 后端自寻全路线

- 分支：`jingjinji-RAM`
- 路网：京津冀 PBF（`osm/jingjinji-latest.osm.pbf`，约 177MB）
- 图缓存：`graph-cache/jingjinji-compliant-time-v2`（RAM 存储）
- 边界：`boundaries/sixth-ring-boundary-jingjinji.geojson`（schema v4 京津冀版，`sourcePbfSha256=2a1bcebc…`）

路由链路：全部由后端自研完成——受控区内合规路线 + 界外 A*（京津冀范围内），前端不调用高德路线规划，无配额消耗。

内存：后端加载图后实测 java 进程约 2.7GB；4G 服务器推荐 `-Xmx2048m`，2G 需要 swap 兜底（不推荐）。

优点：后端自给自足，无第三方路线依赖与配额。
代价：内存占用大；界外规划局限于京津冀路网范围；启动约 2~3 分钟。

技术文档：`docs/plans/京津冀RAM方案.md`
部署清单：`docs/plans/部署上线实施清单.md`

## 3. 方案三：京津冀路网 + MMAP 存储 + 后端自寻全路线

- 分支：`jingjinji-MMAP`
- 路网：京津冀 PBF（`osm/jingjinji-latest.osm.pbf`，约 177MB）
- 图缓存：`graph-cache/jingjinji-compliant-time-v2-mmap`（MMAP 存储）
- 边界：`boundaries/sixth-ring-boundary-jingjinji.geojson`（schema v4 京津冀版）

路由链路：与方案二一致，后端自寻全路线；区别仅在 GraphHopper 图数据存储方式为 MMAP（构图与启动均需 `-Drouting.graph.storage=MMAP`）。

内存：实测 java 进程约 1.5GB，适合 2G 低配（建议加 swap）；寻路耗时毫秒级~1.5s，路线结果与 RAM 方案一致。

优点：内存显著低于 RAM 方案，2G 服务器可用。
代价：MMAP 缓存需单独构图与维护；启动加载较 RAM 略慢；仍局限于京津冀路网范围。

技术文档：`docs/plans/京津冀MMAP方案.md`
部署清单：`docs/plans/部署上线实施清单.md`

## 4. 方案对比

| 项 | 方案一 北京+高德 | 方案二 京津冀 RAM | 方案三 京津冀 MMAP |
|---|---|---|---|
| 分支 | dev / dev-amap-external | jingjinji-RAM | jingjinji-MMAP |
| PBF | beijing（40MB） | jingjinji（177MB） | jingjinji（177MB） |
| 图存储 | RAM | RAM | MMAP |
| 缓存目录 | beijing-compliant-time-v2 | jingjinji-compliant-time-v2 | jingjinji-compliant-time-v2-mmap |
| 边界文件 | sixth-ring-boundary.geojson | sixth-ring-boundary-jingjinji.geojson | sixth-ring-boundary-jingjinji.geojson |
| 界外路线 | 高德 JS API（前端，配额） | 后端 A*（京津冀内） | 后端 A*（京津冀内） |
| 进程内存 | 约 1GB | 约 2.7GB | 约 1.5GB |
| 2G 服务器 | 可（-Xmx1536m） | 需 swap，不推荐 | 可（+swap） |
| 高德配额 | 依赖（场景 3 每次 3 次） | 无 | 无 |
| 路线范围 | 界外全国（高德） | 京津冀 | 京津冀 |

## 5. 已舍弃方案

- `dev-beijing-osrm`：北京图 + OSRM 公共实例界外拼接。OSRM 路线质量不理想，已由方案一（高德 AMap.Driving）取代，分支保留但不再维护。

## 6. 合入策略

- `dev` 承载方案一，作为当前开发与合入主线的基线。
- `jingjinji-RAM`、`jingjinji-MMAP` 为独立保留方案，由各自分支维护。
- `master` 合并操作由人工在本地完成，不通过自动化推送。
