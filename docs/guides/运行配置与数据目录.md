# 运行配置与数据目录

## 1. 目标

运行数据必须与 Git 仓库和 IDE 工作目录解耦。换电脑、换克隆目录或从 IDEA/命令行启动时，不应依赖 `F:\CodexProjects\routing-plan` 之类的机器绝对路径，也不应依赖 `../../data` 这种工作目录敏感路径。

服务运行只需要统一数据根目录；PBF、摄像头、边界、缓存、快照和日志从该目录派生。中国 PBF 下载、区域切分、候选构图、受控区域分析、工具和审查材料属于离线工作，不放进运行数据根。

## 2. 标准目录

Windows 默认根目录为后端启动所在盘的：

```text
\camera-safe-routing-data
```

例如 `server` 位于 `F:` 盘时，Java 会把默认路径解析为：

```text
F:\camera-safe-routing-data\
├─ osm\
│  └─ jingjinji-latest.osm.pbf      当前使用（历史北京文件已清理）
├─ cameras\
│  └─ camera.json                   当前已发布摄像头源快照
├─ boundaries\
│  └─ sixth-ring-boundary.geojson   当前受控区域并集边界（schema v3，已批准）
├─ graph-cache\
│  └─ jingjinji-compliant-time-v2\ 当前源码默认 GraphHopper 缓存（历史缓存已清理）
├─ snapshots\                       路由禁行边持久化快照
├─ downloads\cameras\               摄像头更新候选文件
├─ failed\cameras\                  更新失败的隔离文件
├─ backups\cameras\                 摄像头旧版本备份
└─ logs\
   ├─ camera-safe-routing-server.log 当前服务日志
   └─ archive\                       压缩后的滚动日志
```

仓库同级离线工作区默认是：

```text
F:\CodexProjects\routing-plan\workspace\
├─ downloads\osm\
│  └─ china-latest.osm.pbf          中国源 PBF，只供离线切分
├─ tools\                            osmium、micromamba 等离线工具
├─ work\osm\                         京津冀 PBF 候选
├─ work\graph-cache-candidates\      候选图缓存
├─ work\controlled-area-v1\          并集边界候选与审查报告
├─ work\sixth-ring\                  旧六环边界与拓扑分析产物，可选保留
├─ reports\                          仓库外的大体积或临时报告
├─ reviews\                          人工审查材料
└─ archive\                          离线历史产物
```

后端不会读取 `workspace`。只有已经验证并发布到运行数据根的 `osm/jingjinji-latest.osm.pbf`、`boundaries/sixth-ring-boundary.geojson` 和图缓存才参与服务启动。并集边界已按候选内容正式化（2026-08-12，`approvedForProduction=true`），候选文件保留在 `workspace/work/controlled-area-v1` 作为版本对照。

初始化脚本：

```powershell
Set-Location <仓库的code目录>
.\scripts\init-data-directory.ps1
.\scripts\init-workspace-directory.ps1
```

指定其他根目录：

```powershell
.\scripts\init-data-directory.ps1 -DataRoot 'D:\routing-data'
.\scripts\init-workspace-directory.ps1 -WorkspaceRoot 'D:\routing-workspace'
```

两个脚本都只创建目录，不下载、移动或覆盖数据。`init-data-directory.ps1` 面向服务运行，`init-workspace-directory.ps1` 面向离线处理。

## 3. 后端路径解析

`server/src/main/resources/application.yml` 使用以下优先级：

1. 单项环境变量，例如 `ROUTING_PBF_PATH`。
2. `ROUTING_DATA_ROOT` 加标准相对位置。
3. 当前盘根目录的 `camera-safe-routing-data`。

普通开发建议只设置 `ROUTING_DATA_ROOT`。单项覆盖用于容器挂载、只读 PBF 盘和缓存独立高速盘等特殊部署。

| 环境变量 | 默认相对数据根目录 | 说明 |
|---|---|---|
| `ROUTING_DATA_ROOT` | 当前盘 `\camera-safe-routing-data` | 统一数据根目录 |
| `ROUTING_PBF_PATH` | `osm/jingjinji-latest.osm.pbf` | 当前路网输入 |
| `ROUTING_CANDIDATE_GRAPH_CACHE_PATH` | `graph-cache/jingjinji-compliant-time-v2` | 当前默认时间优先 profile 图缓存 |
| `ROUTING_GRAPH_CACHE_PATH` | `graph-cache/jingjinji` | `CURRENT` 回退缓存已从正式目录移除；如需回退需重新构图并恢复该目录 |
| `SIXTH_RING_BOUNDARY_PATH` | `boundaries/sixth-ring-boundary.geojson` | 受控区域并集边界 GeoJSON；变量名和文件名暂兼容保留 |
| `CAMERA_JSON_PATH` | `cameras/camera.json` | 摄像头源 JSON |
| `CAMERA_SNAPSHOT_PATH` | `snapshots` | 禁行边持久化快照 |
| `CAMERA_UPDATE_DOWNLOAD_PATH` | `downloads/cameras` | 远程更新候选目录 |
| `CAMERA_UPDATE_FAILED_PATH` | `failed/cameras` | 校验或发布失败隔离目录 |
| `CAMERA_UPDATE_BACKUP_PATH` | `backups/cameras` | 正式摄像头源旧版本目录 |
| `APP_LOG_FILE` | `logs/camera-safe-routing-server.log` | 当前服务日志文件 |
| `APP_LOG_ARCHIVE_PATTERN` | `logs/archive/camera-safe-routing-server.%d{yyyy-MM-dd}.%i.log.gz` | 滚动归档文件名模式 |

`server/.env.example` 是变量清单，不会被 Spring Boot 自动加载。IDEA 中应把变量放到 Run Configuration 的 Environment variables；PowerShell 中应在启动 Maven/JAR 的同一进程设置；部署时由服务管理器、容器或系统环境提供。

Linux 服务器不建议直接使用默认 `/camera-safe-routing-data`，除非部署用户确实有该目录权限。推荐明确设置：

```text
ROUTING_DATA_ROOT=/srv/camera-safe-routing-data
```

## 3.1 IDEA 调试启动（正式 / 候选）

前置条件：JDK 21、Maven 3.8+；用 IDEA 打开 `code/server` 目录（后端项目根，模块名 `camera-safe-routing-server`），前端 `code/web` 用 WebStorm 打开。

仓库已提供两个共享运行配置（`server/.run/`），IDEA 打开 `server` 后可直接在 Run 下拉框选择：

- `CameraSafeRoutingServer (正式数据)`：加载当前盘 `\camera-safe-routing-data` 的正式边界、正式缓存与摄像头（全部走 `application.yml` 默认值，无需任何环境变量）。
- `CameraSafeRoutingServer (候选数据)`：通过 `SPRING_PROFILES_ACTIVE=candidate` 激活候选 profile，加载 `workspace/work` 的候选边界与候选缓存，等价于当前命令行验证所用配置。

两个配置的主类都是 `cn.camera.safe.CameraSafeRoutingApplication`，工作目录为项目根 `$PROJECT_DIR$`（即 `server` 目录）。若不想使用共享配置，可手动创建 Run Configuration：Main class 填主类，Working directory 填 `$PROJECT_DIR$`，Environment variables 按下方表格填写。

### 正式数据（跨设备零配置）

正式模式不需要设置环境变量：`application.yml` 默认把数据根解析为后端启动所在盘的 `\camera-safe-routing-data`，缓存默认用 `graph-cache/jingjinji-compliant-time-v2`，边界默认用 `boundaries/sixth-ring-boundary.geojson`。换电脑只需保证该盘存在同一布局的数据根，配置本身无需改动。

### 候选数据（跨设备相对路径）

候选模式设置 `SPRING_PROFILES_ACTIVE=candidate`（运行配置已带），路径由 `server/src/main/resources/application-candidate.yml` 按仓库布局相对推导：

```text
app.routing.graph-cache-path         = ../../workspace/work/graph-cache-candidates/jingjinji-compliant-time-v2-20260807-current
app.routing.candidate-graph-cache-path = ../../workspace/work/graph-cache-candidates/jingjinji-compliant-time-v2-20260807
app.sixth-ring.boundary-path         = ../../workspace/work/controlled-area-v1/controlled-area-boundary-candidate.geojson
```

前提：仓库根 `code` 与离线工作区 `workspace` 位于同一父目录（`routing-plan`），且工作目录为 `server` 模块根（IDEA 配置已满足；命令行启动请先 `cd code/server`）。

注意：

- 正式边界已定版：`F:\camera-safe-routing-data\boundaries\sixth-ring-boundary.geojson` 已替换为 schema v3 并集边界（含 `controlled_area`、`sixth_ring_area`、`tongzhou_area`），`approvedForProduction=true`。`(正式数据)` 配置可直接使用。
- 正式缓存 `F:\camera-safe-routing-data\graph-cache\jingjinji-compliant-time-v2` 为唯一保留的定版缓存，历史缓存已清理。
- 端口冲突：命令行启动的服务默认占用 `8080`，IDEA 调试前先停止旧服务，或通过 `SERVER_PORT` 换端口。
- IDEA 使用自己的 Maven 本地仓库（默认 `~/.m2/repository`），首次运行会自动下载依赖；若机器此前只在临时仓库构建过，请保持网络可用。
- 首次启动需要约 3~4 分钟（路网加载、收费站/互转走廊审计与摄像头快照重建），可通过 `http://localhost:8080/api/v1/readiness` 或启动日志确认 READY。

命令行（PowerShell）手动启动时可使用同样的两种方式：正式模式直接 `java -jar`（不设变量）；候选模式先 `cd code/server` 再 `$env:SPRING_PROFILES_ACTIVE='candidate'; java -jar ...`。如需按机器显式指定路径（容器、独立高速盘等特殊部署），仍可使用第 3 节的环境变量覆盖表，但这些值属于机器相关配置，不应写进共享运行配置或提交到仓库。

## 3.2 并集边界生成（脚本）

受控区域并集边界由 `code/scripts/generate-controlled-area-boundary.ps1` 生成，内部调用 jar 内置的 `boundary-generate` CLI（JTS 面并集），产出 schema v3 候选 GeoJSON 与 Markdown 报告，不再依赖 Maven/JUnit。

默认输入：

- 六环线：`workspace\work\sixth-ring\sixth-ring-lines.geojson`（由 osmium 从 PBF 按 relation r295982 导出）
- 通州行政区：`workspace\work\controlled-area-v1\tongzhou-boundary.geojson`（由主 PBF 按 relation `r2988902` 提取）

默认输出：`workspace\work\controlled-area-v1\controlled-area-boundary-candidate.geojson` 与 `controlled-area-boundary-report.md`。

用法（在 `code` 目录）：

```powershell
.\scripts\generate-controlled-area-boundary.ps1 -MavenLocalRepo "$env:TEMP\routing-plan-m2"
```

可选参数：`-SixthRingBoundary`、`-TongzhouGeojson`、`-Output`、`-Report`、`-DataRoot`、`-MavenLocalRepo`；`-Publish` 在审阅通过后将候选发布到正式目录并置 `approvedForProduction=true`（会要求确认）。

注意：并集边界必须与源 PBF 绑定（`sourcePbfSha256`）。PBF 更新后，需要重新提取六环内侧面与通州行政区（都与新 PBF 哈希一致）再运行脚本，然后走候选审阅 → 真实路线回归 → 发布流程，不能沿用旧边界。

## 3.3 路网 PBF 更新流程（含两个来源文件获取）

更新 PBF 后，边界、图缓存、禁行快照都会因哈希变化而失效，必须按顺序执行以下步骤（命令均已在当前环境验证）。

推荐直接使用部署脚本一条命令完成：构建机执行 `build-deployment-package.ps1`（内部自动切分/提取/边界/构图/校验/打包），服务器执行 `update-routing-data.ps1`。以下手动命令供理解与排查。

### 第 1 步：切分并发布新 PBF

```powershell
# 下载中国 PBF 到 workspace\downloads\osm\china-latest.osm.pbf 后：
.\scripts\prepare-jingjinji-osm.ps1
# 产出 workspace\work\osm\jingjinji-smart-<日期>-<哈希>.osm.pbf（含 restrictions-check 变体）

# 候选回归通过后发布为正式路网：
Copy-Item 'workspace\work\osm\jingjinji-smart-*.osm.pbf' 'F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf'
```

### 第 2 步：提取六环内侧面（来源文件一）

```powershell
$osmium = 'F:\CodexProjects\routing-plan\workspace\tools\osmium-env\Library\bin\osmium.exe'
$pbf = 'F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf'
$ring = 'F:\CodexProjects\routing-plan\workspace\work\sixth-ring\sixth-ring-r295982.osm.pbf'
$lines = 'F:\CodexProjects\routing-plan\workspace\work\sixth-ring\sixth-ring-lines.geojson'

& $osmium getid --overwrite -r --output $ring $pbf r295982
& $osmium export --output $lines $ring
# 生成六环边界（inside_boundary / outside_boundary）：
# mvn "-Dmaven.repo.local=$env:TEMP\routing-plan-m2" `
#   "-Dsixth.ring.lines.geojson=$lines" `
#   "-Dsixth.ring.boundary.output=...\sixth-ring-boundary.geojson" `
#   "-Dsixth.ring.report.output=...\sixth-ring-boundary-report.md" `
#   "-Dtest=SixthRingBoundaryPocTest" test
```

### 第 3 步：提取通州行政区（来源文件二）

```powershell
& $osmium getid --overwrite -r --output '...\controlled-area-v1\tongzhou-boundary.osm.pbf' $pbf r2988902
& $osmium export --output '...\controlled-area-v1\tongzhou-boundary.geojson' '...\tongzhou-boundary.osm.pbf'
```

### 第 4 步：生成并集边界候选

```powershell
.\scripts\generate-controlled-area-boundary.ps1 -MavenLocalRepo "$env:TEMP\routing-plan-m2" `
  -SixthRingBoundary 'F:\CodexProjects\routing-plan\workspace\work\sixth-ring\sixth-ring-boundary.geojson'
```

脚本从正式 PBF 计算 `sourcePbfSha256`，产出候选与报告。

### 第 5 步：回归与发布

1. 候选审阅（报告、地图叠加、通行口审计）。
2. 真实路线回归：`SixthRingRoutePlannerIntegrationTest`（14 条）与 `TollCorridorTopologyRealPbfTest`（华为↔龙意园、徐庄桥互转）。
3. 发布边界：`... -Publish`。
4. **重新构图正式缓存**：新 PBF 哈希与旧 `graph-cache\jingjinji-compliant-time-v2` 不匹配，服务会拒绝启动；用 `java -jar server.jar graph-build` 在空候选缓存目录冷构图 → `graph-check` 校验 → 回归 → 拷贝发布到正式缓存目录（`build-deployment-package.ps1` 已自动完成）。
5. 重启服务（摄像头快照自动重建）→ readiness + 关键路线验证。

六环线、六环边界、通州文件均保留在 `workspace`（离线产物），不发布到正式目录；正式目录只保留边界、PBF、缓存与快照。

## 5. PBF 命名规则

当前和后续文件统一使用小写区域名加 `-latest.osm.pbf`：

| 文件 | 用途 |
|---|---|
| `beijing-latest.osm.pbf` | 历史北京路网，已从正式目录清理，不再维护 |
| `china-latest.osm.pbf` | 中国月度下载源；只放在离线工作区的 `downloads/osm` |
| `jingjinji-latest.osm.pbf` | 当前京津冀路网 |

`latest` 文件表示当前已发布版本，不承担历史追溯。归档文件使用日期和哈希，例如：

```text
beijing-2026-07-29-4def579524c3.osm.pbf
jingjinji-2026-08-01-a1b2c3d4e5f6.osm.pbf
```

下载中的中国 PBF 必须使用 `.part` 或放在离线工作区的 `downloads/osm`。切分产物先写入 `workspace/work/osm`，通过完整性、范围和路线回归后，再人工发布到运行数据根的 `osm/jingjinji-latest.osm.pbf`。

## 6. 图缓存生命周期

GraphHopper 缓存与以下内容绑定：

- PBF SHA-256。
- GraphHopper 版本。
- encoded values 和 profile。
- 图构建方式。

缓存目录中的 `camera-safe-source.sha256` 记录 PBF 哈希，`camera-safe-routing-config.sha256` 记录 GraphHopper 版本、encoded values、profile、turn costs 和权重规则指纹。`COMPLIANT_TIME_V2` 新增 `osm_way_id` 和 `sixth_ring_mainline` 编码，因此与旧缓存结构不兼容。若 PBF 或路由配置与缓存不一致，服务会拒绝启动，而不是静默混用旧 edge ID。候选模式还会拒绝缺失路由配置元数据的历史目录。

更新 PBF 时必须：

1. 停止或保持旧服务继续使用旧目录。
2. 在离线工作区的候选缓存目录构建图，或让停机后的首次启动在新的空运行缓存目录构建图。
3. 重建摄像头禁行边快照。
4. 运行真实匹配、零冲突路线和缓存加载回归。
5. 切换配置并重启。
6. 保留上一版本直到新服务验证通过。

不要把多个地区或多个 PBF 版本写入同一缓存目录。

## 7. 摄像头和快照

`cameras/camera.json` 是当前发布输入。更新前的旧版本进入 `backups/cameras`，校验失败的候选进入 `failed/cameras`。快照文件由后端生成，包含摄像头源哈希、图指纹、安全半径、匹配数、未匹配 ID 和禁行 edge ID。

快照不能跨 PBF 缓存复用。图重建后 edge ID 会变化，必须重新匹配。

生产加载器只排除 `IsSixRingOut` 字符串或数值语义为 `1` 的记录；缺失和非法值保留并计数。后续更新任务和加载器都应执行该规则，形成双重防护。

后端启动时只根据现有 `camera.json` 重建快照，不等待远程下载。定时更新和本机 `/api/v1/admin/camera-data/update` 接口共用候选校验、备份、原子切换和防重入逻辑。相同内容的禁行边快照不会重复写入，旧源、快照和失败候选都会按数量上限清理。

## 8. 日志目录和保留策略

后端日志同时输出到启动控制台和 `logs/camera-safe-routing-server.log`。项目业务日志使用中文；Spring Boot、Tomcat 和 GraphHopper 等依赖框架自身的日志可能仍为英文。

日志跨天或当前文件达到 50MB 时滚动到 `logs/archive` 并使用 gzip 压缩。默认最多保留 30 天且归档总量不超过 2GB，任一限制触发都会删除最旧归档；当前正在写入的日志文件不计入归档数量。服务启动时也会执行一次历史清理。

Windows 实时查看默认数据目录日志：

```powershell
Get-Content 'F:\camera-safe-routing-data\logs\camera-safe-routing-server.log' -Tail 100 -Wait
```

如果设置了 `ROUTING_DATA_ROOT` 或 `APP_LOG_FILE`，应改用对应路径。日志不得包含 Cookie、令牌、密钥或完整用户定位。

## 9. 前端环境变量

Vite 会自动读取 `web/.env.local`，该文件已被 Git 忽略。

| 变量 | 本地联调建议 | 说明 |
|---|---|---|
| `VITE_AMAP_KEY` | 用户填写 | 高德 Web JS Key |
| `VITE_AMAP_SECURITY_CODE` | 用户填写 | 高德安全密钥 |
| `VITE_API_BASE_URL` | 留空 | 使用 Vite `/api` 代理到 8080 |
| `VITE_USE_MOCK_API` | `false` | `true` 时完全使用前端 mock |

修改 `.env.local` 后必须重启 Vite。真实 Key、密钥和本地 HTTPS 证书不得提交到 Git。

## 10. 新电脑接入清单

1. 克隆 `code` 仓库。
2. 安装 JDK 21、Maven 3.8+ 和 Node 24.16.x。
3. 分别运行运行数据目录和离线工作区初始化脚本。
4. 将已切分并验证的 `jingjinji-latest.osm.pbf` 发布到运行数据根的 `osm`。
5. 获取当前 `camera.json` 到运行数据根的 `cameras`。
6. 获取与当前 PBF 哈希匹配、已完成人工批准的受控区域并集 GeoJSON，到运行数据根的 `boundaries/sixth-ring-boundary.geojson`。
7. 在 `web/.env.local` 填写高德配置。
8. 后端首次启动生成缓存、受控区域通行口拓扑、道路分类审计和摄像头快照。
9. 检查 readiness，再启动前端真实联调。
10. 运行验证指南中的默认测试和至少一个真实数据测试。

整个流程不需要写死仓库绝对路径。
