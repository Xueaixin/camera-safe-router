# 运维管理

更新时间：2026-08-12

本文覆盖部署上线、月度路网更新、摄像头数据维护、运维接口、日志与回滚。文中涉及的脚本与 jar CLI 均已实现。

## 1. 部署模型

采用“构建机出包、服务器运行”的两段式部署，把耗时且吃资源的操作（PBF 切分、图缓存构图、边界生成）放在构建机，服务器只负责解压、切换和运行，依赖最小。

| 机器 | 职责 | 依赖 |
|---|---|---|
| 构建机 | 切分 PBF、构图、生成边界、打部署包、冒烟 | JDK 21、osmium、jar（可选 Maven 源码） |
| 服务器 | 首次部署、月度更新、运行服务、摄像头自动更新 | JDK 21、jar、data.zip、运维脚本 |

设计原则：

- 每台机器只提供一个总入口命令，用户不需要逐个执行内部步骤。
- 部署包不携带机器绝对路径，`data.zip` 内部结构即数据根结构，解压即用。
- 缓存与 jar 配套：缓存配置指纹绑定构图时的 jar 路由配置，发布时 jar 与缓存一起交付。
- 服务器不依赖 Maven、源码和 osmium（构图与边界都在构建机完成）。

## 2. 部署产物

`data.zip` 只包含运行必需的四项：

```text
data.zip
├─ osm\jingjinji-latest.osm.pbf            （当前路网，约 177MB）
├─ cameras\camera.json                     （初版摄像头源，约 1.5MB）
├─ boundaries\sixth-ring-boundary.geojson  （schema v4 并集边界，approvedForProduction=true，含 `provincial_border`）
└─ graph-cache\jingjinji-compliant-time-v2\（预构建图缓存，含两个 .sha256 元数据，约 273MB）
```

不打包：`snapshots`、`logs`、`downloads`、`backups`、`failed`（init 脚本建目录，快照启动自动重建）。

## 2.5 数据工具 CLI（jar 内置）

后端 jar 内置三个离线命令，用于构建机出包：

### 2.5.1 graph-build（冷构图）

```text
java -jar server.jar graph-build --pbf <file> --cache-out <dir> [--threads N]
```

参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--pbf` | 是 | 源 PBF 路径 |
| `--cache-out` | 是 | 目标缓存目录，**必须为空或不存在**（避免覆盖已有缓存） |
| `--threads` | 否 | GraphHopper 导入并行线程数，默认 2 |

行为：从 PBF 冷构图，写入缓存目录并生成 `camera-safe-source.sha256`（PBF 哈希）与 `camera-safe-routing-config.sha256`（路由配置指纹）；打印节点/边数、图指纹与耗时。建议构图时加 `-Xmx4g`。

示例：

```powershell
java -Xmx4g -jar server.jar graph-build `
  --pbf F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf `
  --cache-out F:\CodexProjects\routing-plan\workspace\work\graph-cache-candidates\jingjinji-compliant-time-v2 --threads 4
```

### 2.5.2 graph-check（缓存校验）

```text
java -jar server.jar graph-check --pbf <file> --cache <dir>
```

参数：`--pbf`（源 PBF）、`--cache`（已有缓存目录，须含 `properties` 文件）。加载缓存并校验 PBF 哈希与路由配置指纹是否与当前 jar 配套；不匹配时抛错并以非零退出。用于打包冒烟和部署前校验。

示例：

```powershell
java -jar server.jar graph-check `
  --pbf F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf `
  --cache F:\camera-safe-routing-data\graph-cache\jingjinji-compliant-time-v2
```

### 2.5.3 boundary-generate（生成并集边界）

```text
java -jar server.jar boundary-generate --sixth-ring-lines <file> --tongzhou <file>
  --pbf <file> --output <file> [--report <file>] [--approved]
```

参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--sixth-ring-lines` | 是 | 六环线 GeoJSON（osmium 从 PBF 按 relation r295982 导出的 LineString 要素） |
| `--tongzhou` | 是 | 通州面 GeoJSON（osmium 从 PBF 按 relation r2988902 导出） |
| `--pbf` | 是 | 源 PBF，用于计算 `sourcePbfSha256` |
| `--output` | 是 | schema v4 边界输出路径 |
| `--report` | 否 | 可选 Markdown 报告输出 |
| `--approved` | 否 | 生成 `approvedForProduction=true` 的正式版（默认候选 false） |

行为：线合并得到六环内侧面，与通州面做拓扑并集，校验覆盖关系后写出 schema v4（含 `controlled_area`/`sixth_ring_area`/`tongzhou_area`/`provincial_border`）；`provincial_border` 从通州关系 `admin_level=4` 边界 way 提取并线合并，用于通州北京省界普通道路入界禁行。

示例：

```powershell
java -jar server.jar boundary-generate `
  --sixth-ring-lines F:\CodexProjects\routing-plan\workspace\work\sixth-ring\sixth-ring-lines.geojson `
  --tongzhou F:\CodexProjects\routing-plan\workspace\work\controlled-area-v1\tongzhou-boundary.geojson `
  --pbf F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf `
  --output F:\CodexProjects\routing-plan\workspace\work\controlled-area-v1\controlled-area-boundary-candidate.geojson `
  --approved
```

## 2.6 脚本使用手册

### 2.6.2 构建机：出部署包

前提：已执行 `mvn -DskipTests package` 产出 jar；osmium 位于 `workspace\tools\osmium-env`（缺失时运行 `.\scripts\install-osmium.ps1` 用工作区 micromamba 安装，或从已有机器拷贝 `workspace\tools\osmium-env`；脚本检测到缺失会给出该提示）。

已切好的京津冀 PBF：

```powershell
cd F:\CodexProjects\routing-plan\code
.\scripts\build-deployment-package.ps1 `
  -Pbf 'F:\camera-safe-routing-data\osm\jingjinji-latest.osm.pbf' `
  -CameraJson 'F:\camera-safe-routing-data\cameras\camera.json'
```

只有中国 PBF（自动切分）：

```powershell
.\scripts\build-deployment-package.ps1 `
  -ChinaPbf 'F:\CodexProjects\routing-plan\workspace\downloads\osm\china-latest.osm.pbf' `
  -CameraJson 'F:\camera-safe-routing-data\cameras\camera.json'
```

参数：`-ChinaPbf` 与 `-Pbf` 二选一（都填时 `-Pbf` 优先）；`-CameraJson` 必填；`-OutDir` 默认 `workspace\work\deployment-staging\pkg-<时间戳>`；`-DataRoot`/`-WorkspaceRoot`/`-Jar`/`-OsmiumPath`/`-Java` 可选。

内部自动完成：建暂存数据根 → 复制/切分 PBF → osmium 提取六环线与通州面 → `boundary-generate` 生成并发布边界（approved=true）→ `graph-build` 构图 → `verify-data-consistency` 校验 → 打 `data.zip` + 复制 `server.jar`。

产出：

```text
<OutDir>\data.zip     （osm / cameras / boundaries / graph-cache）
<OutDir>\server.jar
```

### 2.6.3 服务器：首次部署

```powershell
.\scripts\deploy-server.ps1 -Package data.zip -Jar server.jar -DataRoot F:\camera-safe-routing-data
```

参数：`-Package`（必填）、`-Jar`（必填）、`-DataRoot`（默认当前盘 `\camera-safe-routing-data`）、`-ServerPort`（默认 8080）、`-CameraUpdateEnabled`（开启摄像头定时更新）、`-SkipStart`（只准备不启动）。

脚本自动完成：建目录 → 解压 → 三哈希校验 → 启动 → 等待 readiness，打印“服务就绪 访问地址… 启动耗时…”。

### 2.6.4 服务器：月度更新与回滚

```powershell
# 更新（备份当前 osm/boundaries/graph-cache 后替换并重启）
.\scripts\update-routing-data.ps1 -Package data-new.zip -Jar server.jar -DataRoot F:\camera-safe-routing-data

# 回滚到最近一次备份
.\scripts\update-routing-data.ps1 -Jar server.jar -DataRoot F:\camera-safe-routing-data -Rollback
```

备份保存在 `<数据根>\backups\routing\<时间戳>\`。`-SkipStart` 可只准备数据不重启。

### 2.6.5 边界生成（单独使用）

```powershell
.\scripts\generate-controlled-area-boundary.ps1
```

默认输入：`workspace\work\sixth-ring\sixth-ring-lines.geojson` + `workspace\work\controlled-area-v1\tongzhou-boundary.geojson` + 正式 PBF；默认输出 `workspace\work\controlled-area-v1\controlled-area-boundary-candidate.geojson`。`-Publish` 生成批准版并发布到正式 `boundaries`。

常用参数：`-SixthRingLines`、`-TongzhouGeojson`、`-Pbf`、`-Output`、`-Report`、`-Publish`、`-Force`。

### 2.6.6 数据一致性校验（单独使用）

```powershell
.\scripts\verify-data-consistency.ps1 -DataRoot F:\camera-safe-routing-data -Jar server.jar
```

校验 PBF↔缓存、PBF↔边界、缓存配置指纹与 jar 配套；任一不匹配非零退出。

### 2.6.7 目录初始化


### 2.6.9 注意事项

- `-ChinaPbf` 与 `-Pbf` 只填一个，都填时 `-Pbf` 优先。
- `graph-build` 要求 `--cache-out` 目录为空或不存在。
- 部署/更新前自动三哈希校验，不匹配直接失败，不会污染现有数据。
- 更新失败可用 `-Rollback` 一键恢复；摄像头数据另有 `backups\cameras` 独立备份。

## 3. 一致性校验

部署/更新前必须满足以下哈希一致，任一不满足服务会拒绝启动：

| 校验项 | 内容 |
|---|---|
| PBF ↔ 缓存 | `jingjinji-latest.osm.pbf` 的 SHA-256 == 缓存 `camera-safe-source.sha256` |
| PBF ↔ 边界 | PBF 的 SHA-256 == 边界 `sourcePbfSha256` |
| jar ↔ 缓存 | 缓存 `camera-safe-routing-config.sha256` 与运行 jar 的路由配置指纹一致 |

注意：缓存指纹只由 GraphHopper 版本、encoded values、profile、turn costs、受限道路条件决定。仅新增功能、接口或业务逻辑不会改变指纹，旧缓存可复用；一旦改动上述路由配置层，必须重新构图。

## 4. 首次部署（服务器）

前置：JDK 21；确认 `ROUTING_DATA_ROOT`（Linux 必须显式设置）。

总入口（已实现）：

```powershell
.\scripts\deploy-server.ps1 -Package data.zip -Jar server.jar -DataRoot F:\camera-safe-routing-data
```

内部等价步骤（当前可手动执行）：

1. `init-data-directory.ps1 -DataRoot <数据根>` 建目录；
2. 校验 data.zip 三哈希一致；
3. 解压到数据根；
4. 配置环境变量：`ROUTING_DATA_ROOT`、`SERVER_PORT`、`CAMERA_UPDATE_ENABLED=true`；
5. 启动 `java -jar server.jar`；
6. 轮询 `/api/v1/readiness` 至 `READY`，验证两条关键路线。

## 6. 摄像头数据维护

- 初版 `camera.json` 放置一次；服务器设置 `CAMERA_UPDATE_ENABLED=true` 后每天按 `CAMERA_UPDATE_CRON`（默认 `0 15 3 * * *`，Asia/Shanghai）自动从 `https://www.jjz365.cn/CameraData/GetAllRing` 拉取并发布。
- 更新流程包含：源 SHA-256 变化检测、条数/匹配率/禁行边变化率校验、原子发布、旧版本备份、失败文件隔离；相同内容不重复发布。
- 手动立即更新与手动重建快照见第 7 节 admin 接口。

## 7. 运维接口

鉴权说明：`/api/v1/admin/*` 仅允许本机调用（127.0.0.1 / ::1）。非本机访问返回 `503`（错误码 `ROUTING_NOT_READY`，消息“管理端点仅允许本机访问”）。如需经反向代理暴露，必须在代理层加认证，不得无保护暴露公网。

### 7.1 GET /api/v1/health（进程存活）

```text
200 {"status":"UP"}
```

用于负载均衡/进程探活，不校验依赖是否就绪。

### 7.2 GET /api/v1/readiness（就绪检查）

`200` 表示可接受路线请求；未就绪时返回 `503`。响应字段：

| 字段 | 说明 |
|---|---|
| status | `READY` / `NOT_READY` |
| graphLoaded | 路网（GraphHopper）是否加载完成 |
| sixthRingTopologyLoaded | 六环通行口/道路分类/走廊拓扑是否就绪 |
| cameraSnapshotLoaded | 摄像头快照是否加载 |
| blockedEdgesLoaded | 禁行边是否与快照版本一致 |
| reason | 未就绪原因（就绪时为 null） |

示例：

```powershell
Invoke-WebRequest -Uri 'http://localhost:8080/api/v1/readiness' -UseBasicParsing | Select-Object -ExpandProperty Content
```

### 7.3 POST /api/v1/admin/camera-snapshots/refresh（重建快照）

从配置的本地 `camera.json` 显式重建摄像头与禁行边快照（异步任务）。

```text
202 {"jobId":"<uuid>","status":"ACCEPTED"}
409 已有刷新/更新任务执行中（CAMERA_UPDATE_ALREADY_RUNNING）
503 服务未就绪
```

示例：

```powershell
Invoke-WebRequest -Uri 'http://localhost:8080/api/v1/admin/camera-snapshots/refresh' -Method Post -UseBasicParsing
```

### 7.4 POST /api/v1/admin/camera-data/update（立即更新摄像头数据）

立即下载、校验并发布最新摄像头数据，与定时任务复用同一流程和防重入锁。

```text
200 CameraUpdateResult
409 已有摄像头更新或快照刷新执行中
503 服务未就绪 / 更新失败
```

`CameraUpdateResult` 主要字段：

| 字段 | 说明 |
|---|---|
| status | `UPDATED` / `NO_CHANGE` |
| sourceSha256 / previousSourceSha256 | 新源/旧源 SHA-256 |
| sourceRecordCount / retainedRecordCount / excludedRecordCount / unrecognizedIsSixRingOutCount | 源条数、保留、排除、无法识别计数 |
| restrictedCameraCount / outsideControlAreaCameraCount | 受控摄像头数、界外解禁数 |
| controlBoundaryVersion | 当前边界版本 |
| matchedCameraCount / unmatchedCameraCount | 道路匹配数/未匹配数 |
| blockedEdgeCount | 禁行基础边数 |
| completedAt | 完成时间 |

示例：

```powershell
Invoke-WebRequest -Uri 'http://localhost:8080/api/v1/admin/camera-data/update' -Method Post -UseBasicParsing
```

### 7.5 GET /api/v1/camera-snapshots/current（查看当前版本）

只读查看当前摄像头快照与禁行边版本，便于核对部署后版本一致。

## 8. 日志与监控

- 日志：`<数据根>\logs\camera-safe-routing-server.log`，单文件 50MB 滚动、归档最多 30 天/2GB，启动时清理超限归档。
- 启动阶段日志：路网加载、六环通行口拓扑、道路分类（全边分区/连接器/收费站走廊/互转走廊）、控制释放点、快照发布各阶段均有开始/完成日志；收费站走廊构建（通常是最耗时阶段）按 25% 输出进度。
- 服务就绪日志：快照首次发布完成（readiness 变为 READY）时打印访问地址（`http://localhost:<port>`）、启动耗时与就绪/路线接口路径。
- 启动审计日志：道路分类审计（`road-zone-v4` 指纹）、收费站走廊审计（入口/出口数量）、互转走廊审计（R-H-T 数量）、快照发布版本。
- 建议监控点：`readiness` 轮询；日志中“摄像头数据更新失败/快照刷新失败”关键字；快照版本与边界版本变化。

## 9. 回滚

- 路网更新：`update-routing-data.ps1 -Rollback` 恢复上一版 `osm/boundaries/graph-cache`。
- 摄像头数据：自动更新前旧版本进入 `<数据根>\backups\cameras`，失败候选进入 `<数据根>\failed\cameras`。
- 图缓存：新旧缓存使用不同目录，不手工覆盖正在运行的缓存；切换前旧目录保留，验证通过后再清理。

## 10. 版本说明

- 算法/方案版本：V2.5（当前，通州北京省界入界禁行，schema v4 候选待批准）；V2.2/V2.3/V2.4 为历史基线。
- 边界文件格式：schemaVersion=4（含 `controlled_area`/`sixth_ring_area`/`tongzhou_area`/`provincial_border`）；加载器兼容旧 v3（无省界线时不启用入界禁行）。
- 道路分类指纹：`road-zone-v4`。
- 应用版本：后端 `0.1.0-SNAPSHOT`、前端 `0.1.0`；API 契约 `1.5.0`（OpenAPI 3.0.3）。
