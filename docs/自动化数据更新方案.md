# 自动化数据更新方案

> 当前优先级说明：摄像头日更能力已经实现；中国 PBF 月更、自动构图和生产发布暂缓，待线路规划算法生产化完成后继续。本文件保留为后续工程化方案，不代表当前开发主线。

## 1. 目标和边界

下一阶段自动化分成两条独立流水线：

- 摄像头数据：建议每天更新，只重建摄像头和禁行边快照。
- OSM 路网：建议每月更新，从中国 PBF 切分京津冀并重建完整路网缓存。

两条流水线不能互相隐式触发，也不能直接覆盖正在使用的数据。任何校验失败都必须保留上一有效版本。

首版按单服务器、单后端实例部署，由 Spring Boot 内部定时任务执行摄像头日更，不需要额外配置 Windows Task Scheduler、systemd timer 或 cron。OSM 更新耗时长且需要重建服务，仍采用独立运维任务。

## 2. 摄像头每日更新

### 2.1 来源

```text
POST https://www.jjz365.cn/CameraData/GetAllRing
Body: empty
```

上线前需要确认接口使用许可、认证方式、速率限制、可用性和字段变更通知。不得把第三方 Cookie、令牌或高德密钥写入源码。

### 2.2 建议频率

- 默认计划为每天 `03:15 Asia/Shanghai` 执行一次。
- 首版失败后保留当前版本并等待下一次计划任务，也可从本机手动重试。
- 连续失败不影响现有路线服务，但必须告警。

频率由 `CAMERA_UPDATE_CRON` 和 `CAMERA_UPDATE_ZONE` 配置。定时更新默认关闭，确认接口使用许可后设置 `CAMERA_UPDATE_ENABLED=true` 开启。

### 2.3 流水线

```text
Spring 定时任务或本机管理接口触发
  -> POST 下载远程 JSON 并限制状态码、类型、超时和大小
  -> 保存候选到 downloads/cameras
  -> JSON 结构和字段校验
  -> 统计源记录及字段分布
  -> 排除 IsSixRingOut 语义为 1，保留并统计缺失或非法值
  -> ID、坐标、数量变化校验
  -> 从候选文件构建禁行边快照并检查匹配率和禁行边数量变化
  -> 备份当前 camera.json
  -> 在同一发布锁内原子替换 camera.json 并切换内存快照
  -> 清理超过上限的旧源、失败候选和禁行边快照
```

### 2.4 校验规则

至少检查：

- HTTP 成功、响应体非空且可解析为预期数组。
- 每条记录含有效 `Id/Lng/Lat`；统计 `IsSixRingOut` 的存在性、类型和值分布。
- 排除字符串或数值语义为 `1` 的记录；`0`、缺失和非法值均保留，后两类单独计数并告警。
- ID 不为空；同坐标不同 ID 不盲目去重。
- 经纬度在合理中国范围，转换后仍在路网候选范围。
- 总数相对上一版本的变化超过配置阈值时停止自动发布。
- 30 米匹配率或禁行边数显著下降时停止发布。
- 候选快照能够持久化。固定零冲突路线仍由真实数据集成测试覆盖，不在每日任务中重复执行。

建议把数量变化阈值、最小匹配率和允许的字段缺失数放入版本化配置，而不是散落在脚本中。

### 2.5 原子发布和回滚

- 下载、过滤和报告都写入 `downloads` 或 `work`。
- 候选文件与最终 `cameras/camera.json` 必须位于同一文件系统，使用原子重命名发布。
- 发布前把当前文件复制到 `backups/cameras/camera-<hash>.json`。
- 候选构建或发布失败时不替换正式文件，进程继续使用旧内存快照。
- 后端自身仍应执行“只排除 `IsSixRingOut=1`”过滤，不能只信任更新脚本。
- 相同摄像头源和禁行边内容不会重复生成快照；备份、失败候选和快照分别按配置数量保留。

### 2.6 建议实现形态

首版由 `@Scheduled` 触发同一个同步更新服务，手动入口为：

```http
POST /api/v1/admin/camera-data/update
```

接口仅允许本机访问。定时调用和手动调用共享防重入锁；已有更新或快照刷新正在运行时不会并发发布。服务重启不主动下载，而是先用现有 `cameras/camera.json` 重建禁行边快照，保证远程接口故障不阻塞启动。

该形态适用于单实例部署。未来扩展为多实例时，应只允许一个实例启用内部定时任务，或改用 Kubernetes CronJob 等集中调度方式。

## 3. OSM 月度更新和京津冀切分

### 3.1 来源和命名

```text
中国：http://download.openstreetmap.fr/extracts/asia/china-latest.osm.pbf
```

当前使用 `jingjinji-latest.osm.pbf`。它由中国源离线切分，后续月更仍使用相同发布文件名。

建议每月第一个周日 `02:00 Asia/Shanghai` 下载，避开摄像头日更窗口。下载和构图可能持续数小时，调度任务必须禁止重入。

### 3.2 多线程下载

服务器自动化建议使用 aria2，而不是自己维护分片 HTTP 实现：

```powershell
aria2c.exe `
  --continue=true `
  --max-connection-per-server=8 `
  --split=8 `
  --min-split-size=16M `
  --auto-file-renaming=false `
  --allow-overwrite=true `
  --dir="$routingDataRoot\downloads" `
  --out="china-latest.osm.pbf.part" `
  "http://download.openstreetmap.fr/extracts/asia/china-latest.osm.pbf"
```

如果数据源提供 HTTPS，应优先 HTTPS。仅有 HTTP 时不能依赖传输安全，必须结合文件结构检查、来源元数据、大小异常检测和本地哈希归档。

### 3.3 京津冀切分

首版已采用带缓冲区的固定矩形和 `smart` 策略，既补全跨界道路，也补充相交 multipolygon 依赖。验证边界：

```text
west=113.0, south=35.5, east=120.5, north=43.0
```

该范围覆盖北京、天津和河北并预留跨界道路缓冲，已通过 way 引用、转向限制、GraphHopper 构图、四条跨城、五条北京边缘和两条真实无合规路线回归。当前固定夹具不代表全部路线质量，后续 PBF 候选仍必须重复运行完整回归。

示例命令：

```powershell
.\scripts\prepare-jingjinji-osm.ps1 -DataRoot $routingDataRoot
```

如果后续要求严格行政区数据，可改用北京、天津、河北联合多边形，但路由产物仍建议在行政边界外保留道路缓冲区。

### 3.4 路网候选验证

切分完成后不能直接替换当前文件。必须在版本化候选目录中：

1. 记录源 URL、下载时间、Content-Length、源哈希、切分配置、产物哈希和 osmium 版本。
2. 导入 GraphHopper 新缓存，例如 `graph-cache/jingjinji-<hash12>`。
3. 记录节点、边、可驾车索引边、边界、峰值内存和导入耗时。
4. 重新生成摄像头匹配报告和禁行边快照。
5. 运行北京固定路线、北京边缘、北京到天津、北京到河北和跨城无路异常用例。
6. 确认缓存冷启动和只用缓存启动均通过。
7. 审核磁盘空间，至少同时保留当前版本、候选版本和下载临时文件。

京津冀首版只验证统一路网中的基础跨城可达性和摄像头硬避让，不立即改变路线权重。后续单独评估“跨区域路线优先进入六环路”策略，并在明确适用范围、道路定义、绕行上限、收费偏好及软硬约束后再进入算法设计。

### 3.5 发布方式

当前后端不支持运行中热换路网。推荐蓝绿数据目录：

```text
graph-cache\jingjinji-<old-hash>\
graph-cache\jingjinji-<new-hash>\
osm\archive\jingjinji-<date>-<hash>.osm.pbf
osm\jingjinji-latest.osm.pbf
```

本地开发默认读取 `osm/jingjinji-latest.osm.pbf` 和 `graph-cache/jingjinji`，不需要额外环境变量。自动发布仍应先在版本化候选目录验证；维护窗口停止服务后再提升当前 PBF 和缓存，重启、等待 readiness 并运行 HTTP 冒烟。失败时恢复上一份 PBF、缓存和旧服务。

不要在已有缓存目录中覆盖 PBF。当前后端会检测哈希不一致并拒绝加载，这属于预期保护。

## 4. 版本清单和报告

每次自动任务建议生成一个 UTF-8 JSON 清单和一份中文 Markdown 报告，至少包含：

- 任务类型、开始/结束时间和退出状态。
- 数据源 URL、HTTP 元数据和工具版本。
- 输入、输出 SHA-256 和字节数。
- 过滤、切分和阈值配置版本。
- 摄像头源数、纳入数、排除数、匹配率和未匹配数。
- 路网节点、边、边界、缓存目录和图指纹。
- 执行过的测试及其真实结果。
- 发布版本、上一版本和回滚位置。

日志和报告不能包含 Cookie、令牌、密钥或完整用户定位。

## 5. 失败策略

| 失败点 | 行为 |
|---|---|
| 下载超时或中断 | 保留 `.part` 供续传，不影响 current |
| JSON/PBF 解析失败 | 隔离候选，不发布 |
| 记录数异常 | 停止并告警，等待人工审核 |
| 摄像头匹配率下降 | 停止并生成差异报告 |
| GraphHopper 构图失败 | 删除或隔离候选缓存，继续旧图 |
| 真实路线回归失败 | 禁止切换 |
| 新服务 readiness 失败 | 回滚旧路径和旧服务 |
| 报告或清单写入失败 | 视为任务失败，不发布 |

自动化的首要目标是可回滚和不污染当前版本，不是无条件追求“最新”。
