## 3. 下一阶段：摄像头自动化

执行顺序：

1. 实现独立数据更新任务，远程获取原始响应并保留原始归档。
2. 完成结构、数量变化、ID、坐标和字段分布校验。
3. 排除 `IsSixRingOut=1` 后在同一文件系统原子替换 `cameras/map.json`，缺失和非法值保留并告警。
4. 仅从本机触发刷新，确认新快照发布且旧快照可回滚。
5. 增加失败告警、连续失败统计和人工强制回滚入口。

完成定义：远程失败或坏数据不能污染当前文件；服务持续使用上一有效快照；报告明确原始条数、过滤条数、匹配数和版本哈希。

## 4. 后续阶段：京津冀路网

执行顺序：

1. 固定中国源 URL、下载器、计划频率和空间预算。
2. 用 osmium 从 `china-latest.osm.pbf` 切分带缓冲区的京津冀区域。
3. 校验 PBF 结构、边界、完整 way 和代表性跨城路线。
4. 在新缓存目录离线构建 GraphHopper 图。
5. 对当前摄像头重新匹配并运行 20/30/50 米报告。
6. 运行北京固定路线、北京边缘、北京到天津和河北代表路线。
7. 通过发布门槛后切换配置并重启服务，旧版本保留至少一个周期。

详细方案见 [自动化数据更新方案](自动化数据更新方案.md)。

## 5. 远期导航阶段

网页可以继续显示实时位置，但正式导航需要评估原生 App 或跨端方案，重点包括：

- 前后台连续定位权限和系统生命周期。
- 偏航检测与自动重新规划节流。
- 路口级指令、语音播报和航向。
- 弱网、离线、锁屏和省电策略。
- 用户隐私、轨迹最小化和数据保留政策。

后端 API 应保持客户端无关；导航扩展不应破坏当前 Web 手动重算契约。

## 7. 发布阻断条件

出现任一情况不得称为可发布：

- 成功路线的 `cameraConflictCount` 非零。
- 禁行没有发生在 GraphHopper 搜索期间。
- QueryGraph 可以绕过禁行基础边。
- PBF 与缓存哈希不一致。
- 新摄像头数据未经校验或更新失败时覆盖旧快照。
- 前端直接把 WGS84 定位绘制到高德地图。
- 手动重新规划失败后清空旧路线。
- 真实 Key、证书、PBF、缓存或快照进入 Git。
- 未执行的 IDE、构建或手机验证被描述为已经通过。
