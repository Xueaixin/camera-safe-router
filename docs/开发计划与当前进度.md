## 3. 摄像头自动化剩余工作

剩余开发任务：

1. 增加人工选择备份版本的回滚入口，复用候选校验和原子发布流程。
2. 接入连续失败监控告警。

生产环境的数据源许可确认、定时运行观察、阈值确认和摄像头坐标控制点核验由使用方执行，不计入后续编码任务。摄像头源仍按原始字节 SHA-256 比较；数组顺序、字段顺序或排版发生变化时视为新版本并重新构建快照，不增加业务内容指纹。

完成定义：远程失败或坏数据不能污染当前文件；服务持续使用上一有效快照；报告明确原始条数、过滤条数、匹配数和版本哈希。

### 4.1 跨区域路线算法备注

首步先保证北京、天津、河北之间能够使用同一份路网稳定规划并继续硬避开摄像头。当前算法不包含六环路偏好。

后续需要单独讨论“京津冀跨区域路线是否应优先进入六环路”的策略，至少明确适用的起终点范围、所谓进入六环路的道路定义、允许增加的距离和时间、收费高速偏好，以及该策略是软权重还是硬约束。在这些业务规则确定前只保留需求记录，不直接修改路线权重。

详细方案见 [自动化数据更新方案](自动化数据更新方案.md)。

## 5. 远期导航阶段

网页可以继续显示实时位置，但正式导航需要评估原生 App 或跨端方案，重点包括：

- 前后台连续定位权限和系统生命周期。
- 偏航检测与自动重新规划节流。
- 路口级指令、语音播报和航向。
- 弱网、离线、锁屏和省电策略。
- 用户隐私、轨迹最小化和数据保留政策。

后端 API 应保持客户端无关；导航扩展不应破坏当前 Web 手动重算契约。

## 7. 发布阻断条件

出现任一情况不得称为可发布：

- 成功路线的 `cameraConflictCount` 非零。
- 禁行没有发生在 GraphHopper 搜索期间。
- QueryGraph 可以绕过禁行基础边。
- PBF 与缓存哈希不一致。
- 新摄像头数据未经校验或更新失败时覆盖旧快照。
- 前端直接把 WGS84 定位绘制到高德地图。
- 手动重新规划失败后清空旧路线。
- 真实 Key、证书、PBF、缓存或快照进入 Git。
- 未执行的 IDE、构建或手机验证被描述为已经通过。
