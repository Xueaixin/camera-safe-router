# 产品需求与技术方案

## 1. 产品目标

首期提供一个北京区域的移动端优先网页：用户选择起点和终点，系统返回一条在当前路网和摄像头快照下零冲突的驾车路线，并在高德地图上展示路线、摄像头和当前位置。

“避开摄像头”是硬约束，不是风险分或路线偏好。如果所有候选路线都违反当前禁行快照，接口必须返回无合规路线，前端不得绘制一条已知违规的降级路线。

## 2. 用户场景

### 2.1 首次规划

1. 用户通过高德搜索、地图点选或当前位置设置起点。
2. 用户设置终点并发起规划。
3. 前端显式携带坐标系和坐标来源。
4. 后端在单个不可变快照上规划并校验。
5. 前端展示路线、距离、预计时间、步骤和摄像头点位。

### 2.2 当前位置显示

- 浏览器持续提供当前位置时，只更新地图位置标记和精度圆。
- 定位变化本身不触发路线请求。
- 用户拖动地图后，定位更新不会强制把视野拉回。

### 2.3 手动重新规划

- 用户点击重新规划后，使用最近一次有效浏览器位置作为 WGS84 起点。
- 终点保持原路线终点不变。
- 请求期间旧路线继续显示。
- 成功后原子替换路线和摘要；失败时保留旧路线并显示原因。

## 3. 首期范围

已纳入：

- 北京 PBF 实际覆盖范围内的驾车路线。
- 30 米摄像头安全半径。
- 首期忽略摄像头方向，匹配道路正反方向都禁行。
- 起终点搜索、地图点选、当前位置、路线步骤。
- 当前视野摄像头查询与地图渲染。
- 手动重新规划。
- health、readiness、快照状态和本机刷新接口。

暂不纳入：

- 自动偏航重算和语音导航。
- 后台持续定位和轨迹上传。
- 多条备选路线、路线收藏和用户账户。
- 公交、步行、骑行和货车模型。
- 摄像头拍摄方向、主辅路及高架层级的精细语义匹配。
- 服务运行期间热切换整套路网。
- 全国在线路线服务。

## 4. 关键不变量

1. 每个成功路线响应的 `cameraConflictCount` 必须等于 `0`。
2. 禁行发生在 GraphHopper 搜索期间，不允许仅在生成路线后过滤。
3. QueryGraph 虚拟边必须继承对应基础边及方向的禁行状态。
4. JTS 使用最终路线几何做独立校验；发现任何冲突即返回业务错误。
5. 一次请求只能读取同一个摄像头/禁行边快照版本。
6. 快照刷新失败时保留进程内上一有效快照。
7. 前端拒绝非零冲突、未知坐标系或少于两个几何点的“成功”响应。
8. 浏览器位置更新不得自动发起路线规划。

## 5. 系统架构

### 5.1 前端

`web/src` 按职责分为：

| 目录 | 职责 |
|---|---|
| `app` | 应用外壳和页面布局 |
| `components/map` | 地图容器、路线、当前位置、摄像头和工具栏 |
| `components/route` | 起终点输入、规划面板、摘要和步骤 |
| `stores` | 路线、定位和地图状态机 |
| `services` | HTTP API、协议校验和错误处理 |
| `maps` | 高德与 mock 地图适配层 |
| `composables` | 定位和摄像头视野查询 |
| `mocks` | 不依赖真实 Key/后端的开发夹具 |

高德只负责底图、搜索和展示坐标，不参与产品路线规划，也不决定路线是否安全。

### 5.2 后端

`server/src/main/java/cn/camera/safe` 按职责分为：

| 包 | 职责 |
|---|---|
| `api` | Controller、错误体、请求 ID 和本机管理保护 |
| `application` | 初始化、路线、摄像头查询和刷新用例 |
| `camera` | JSON 加载、数据校验、快照和空间索引 |
| `coordinate` | WGS84/GCJ-02 类型、校验和转换 |
| `routing` | GraphHopper、路网索引、禁行边、路线引擎和快照持久化 |
| `validation` | 与路线搜索解耦的 JTS 最终几何校验 |
| `config` | Spring Boot 配置和有界执行器 |

### 5.3 路线生成流程

```text
请求坐标校验
  -> 转换为 WGS84
  -> 校验起终点是否在路网和限制区
  -> 获取一个不可变 RoutingSnapshot
  -> GraphHopper flexible A*/Dijkstra 搜索期硬禁边
  -> 得到候选路线几何
  -> JTS 对当前快照做独立冲突检查
  -> 转换为 GCJ-02 响应
  -> 前端协议校验并绘制
```

## 6. 摄像头与道路匹配

摄像头源坐标当前按 GCJ-02 解释并转换为 WGS84。后端为所有可驾车基础边建立空间索引，查询点位安全圆附近候选边，再使用精确几何距离决定是否命中。首期命中的基础边双向禁行。

30 米匹配只证明附近存在可驾车边，不证明命中了正确的主路、辅路、高架或匝道层级。自动统计必须配合人工控制点和典型复杂路口抽样。

当前生产加载器仍读取全量 6,797 条记录；`IsSixRingOut = 0` 过滤是下一阶段必须完成的后端任务，不能只依赖报告侧过滤。

## 7. 性能设计

- GraphHopper 图在进程内加载，避免每次请求重新解析 PBF。
- 路网可驾车边索引和摄像头空间索引在快照构建时一次生成。
- 禁行状态使用不可变位集合，请求读取无锁快照。
- 路线计算使用有界线程池、队列、超时和最大访问节点限制。
- 动态禁行要求 flexible routing，当前不启用 CH/LM 预计算捷径。
- 首次导图成本较高，后续从同版本图缓存加载。

性能指标必须通过目标机器实测，不能仅依据单次开发机日志承诺。扩大到京津冀后需要重新测量导图峰值内存、缓存大小、启动时间和长距离路线 P95。

## 8. 扩展边界

- App 或未来导航客户端复用现有 HTTP API和坐标契约。
- 自动更新摄像头只替换摄像头源文件并触发新快照，不修改路网。
- OSM 路网更新需要新缓存、新禁行边和全套真实回归，不支持直接覆盖运行中的图。
- 京津冀扩展优先使用中国 PBF 离线切分，不拼接边界互相截断的多个城市小 PBF。
- PostgreSQL/PostGIS、方向匹配、路线历史和正式导航均保持为后续独立阶段。
